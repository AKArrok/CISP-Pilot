# 可复现可靠性门禁

## 目的

本门禁证明当前代码可以在隔离环境中完成数据库初始化和自动化回归，并约束测试不得污染开发集构建产物。它不证明题目归因的泛化准确率，也不替代独立双人盲审 holdout。

## 单命令入口

运行：

```bash
python tests/run_isolated_suite.py
```

脚本会：

1. 在项目内创建一次性目录，避开不可写的系统临时目录。
2. 清空进程级 `DATABASE_URL` 和 MySQL 密码，显式指定临时 `CISP_DB_PATH`。
3. 使用 `scripts/build_taxonomy.py --import-db --db-only` 从当前 1360 题构建产物初始化 SQLite。
4. 对题库、清单、知识点、题目标签和题目归因文件做前后 SHA-256 校验。
5. 使用隔离的 pytest 临时目录运行完整测试。
6. 退出时删除临时数据库和测试目录。

2026-09-24 本地隔离验收为 `229 passed`；不含本地数据资产的 CI 快照为 `216 passed, 13 skipped`，13 项均通过精确跳过审计；四组浏览器 E2E 全部通过。另用 Python Playwright 在临时库上验证归因审阅 30 → 60 条、总计 1360 条、题号筛选和 390px 窄屏无横向溢出。
CI 同款 `ruff check .` 已在全仓库实际通过；没有通过扩大 ignore 列表规避错误。

## 两层自动化证据

GitHub workflow 配置了全仓库静态检查和完整离线 pytest。CI checkout 不含真实题库、课件切片、向量、manifest 和真实课件 PDF，因此相关测试以明确的缺资产原因跳过；其余归因纠错、画像隔离、readiness、缓存、迁移和算法测试全部执行。CI 安装 `pymupdf` 以运行不依赖真实 PDF 的表格算法测试；不安装离线测试不会加载的 `sentence-transformers`/`torch`。

本地 `tests/run_isolated_suite.py` 使用当前 1360 题构建产物初始化临时数据库，执行 Alembic head 和全部 229 项测试，并校验构建产物哈希未变化。另在严格排除 `.env`、`.venv`、`data/`、`.git` 和缓存目录的临时工作区模拟干净 CI checkout，结果为 `216 passed, 13 skipped`；13 项均明确依赖未提交的真实资产。该结果来自本地快照，尚不是远程 GitHub CI 运行记录。

`tests/run_ci_suite.py` 还会拒绝混入本地真实资产的 CI checkout，并精确核对 13 个预期资产依赖 skip 的测试节点，其中包含真实课件 PDF 提取冒烟测试。出现新增 skip、预期节点未收集或某项 skip 被错误改名，CI 都会失败。

两层证据不能互换：本地干净快照通过证明当前工作区在无私有资产环境中可复现；实际 GitHub CI 仍需提交后触发。本地隔离门禁通过证明当前开发机上的真实数据资产与代码兼容。二者都不证明 holdout 泛化准确率。

## 数据库目标不变量

显式 `DATABASE_URL` 是权威数据库目标：

- Alembic 不再把 SQLite URL 当作 MySQL URL处理后静默回退。
- 应用存储层原生支持 `sqlite:///...`。
- 回归测试将 `DATABASE_URL` 和 `CISP_DB_PATH` 分别指向目标库与诱饵库，并断言只创建目标库。
- 未显式设置 `DATABASE_URL` 时，应用才使用 MySQL 配置或默认 SQLite 路径。

任何迁移验收都必须使用临时目标；不得为了测试通过而同步、重建或修改默认业务库。

2026-09-24 对默认 `data/cisp_qa.db` 的只读快照：revision 为 `c8d9e0f1a2b3`，`questions` 为 1360 行，`question_attributions` 为 0 行；文件最后写入时间仍为 2026-09-15 11:36:10 UTC。代码声明的 head 是 `f1a2b3c4d5e6`，所以隔离库通过不代表默认业务库已可用。未迁移、未导入、未改写默认库；真实部署前须另行安排经授权的备份、迁移和归因导入，再复核 `/api/ready`，不能以本地测试结果代替。

## 运行时健康检查

服务提供两个只读端点：

- `GET /api/health`：仅证明 Web 进程存活。
- `GET /api/ready`：同时检查数据库 Alembic revision 是否等于代码声明的 head，以及题库、向量和 manifest 是否一致；全部满足才返回 HTTP 200。
- revision 缺失或落后返回 HTTP 503 和 `migration_required`；迁移已到 head 但资产不一致返回 HTTP 503 和 `assets_invalid`。
- 中文页面在启动时先检查 readiness；未就绪会显示明确维护原因、禁用问答和刷题，并停止知识域与画像请求。

`storage.db.SCHEMA_HEAD` 有测试与 Alembic 迁移图的真实 head 对照，新增迁移却忘记更新运行时声明会直接失败。完整隔离回归与浏览器 E2E 都会先在临时 SQLite 上执行 `alembic upgrade head`；浏览器 E2E 以 `/api/ready` 而不是普通页面作为启动成功条件。

浏览器验收覆盖六段链路：数据库迁移缺失的 503 维护态、题库资产失效的 503 维护态、200 后的诊断与常规作答、模拟纠错及灰度卡四态（空、正常、账本警示、错误）、真实归因纠错、probable 题错答后实际插入校准题并显示中文 `0/2` 证据进度。两种维护态都断言页面显示对应中文原因、禁用业务控件，并且不会提前加载知识域或画像；灰度卡另验证非准确率标识和桌面/窄屏无横向溢出。
## 服务启动不变量

FastAPI 使用 lifespan 执行启动预热，不再使用已弃用的 `on_event("startup")`。自动测试确认每个应用生命周期只执行一次预热；完整回归不再产生 FastAPI 生命周期弃用警告。

## Dense 检索状态

`ENABLE_DENSE_RETRIEVAL=false` 表示有意只使用 BM25：

- 不加载 embedding，也不记为运行时 dense 降级；`config.validate()` 不再强制要求 embedding 凭据；
- 检索缓存键明确区分 dense 开启与关闭；
- embedding 在运行中首次失败时，BM25 兜底结果不会写入故障前计算的 dense 缓存键；
- 浏览器 E2E 使用该显式模式，因此预期的 BM25 测试链路不会制造 ERROR 堆栈。

真正的 embedding 网络或额度故障仍走 `ALLOW_DENSE_DEGRADATION`，置位 `_dense_degraded` 并保留错误日志，两种状态不会混淆。
## 磁盘缓存不变量

Embedding 与 rerank 缓存共同使用原子 JSON 写入：

- 每次写入使用同目录唯一临时文件，避免并发进程争用固定 `.tmp` 文件。
- 完成 JSON 写入后使用 `os.replace` 原子替换。
- Windows 短暂文件锁只重试 3 次，退避总时长有明确上限；持续失败仍抛出异常。
- 无论成功失败都尝试清理本次唯一临时文件。

缓存测试连续运行五轮，共 45 项全部通过；另有确定性测试模拟前两次 `PermissionError`，确认第三次替换成功。Rerank 网络异常路径也有独立测试，避免错误处理因缺少 `httpx` 导入而二次失败。

## 证据边界

这些门禁能够证明：

- Alembic 能在指定的新 SQLite 上升级到 head；
- 旧结构数据经过新增迁移后仍保留；
- 应用和迁移不会把显式 SQLite 目标静默替换成其他数据库；
- 当前自动化测试在完整隔离库上通过；
- 浏览器诊断与归因纠错链路可以运行。

这些门禁不能证明：

- 当前归因模型在独立 holdout 上的准确率；
- 用户纠错计数等同于模型正确率；
- 未经双人独立审校的数据可以作为泛化金标。
