# 归因纠错、画像重放与灰度口径

## 目标

本闭环处理“题目被归到了错误知识点”这一类反馈。用户纠错是当前学习线程内的显式标签，不会覆盖全局分类结果，也不会传播到其他学习者。

它解决的是归因可靠性与画像可逆性，不是泛化准确率评测。没有独立金标和人工盲审时，任何纠错数、校准数或路由一致率都不能命名为准确率。

## 数据边界

- `question_attributions`：系统生成的全局候选快照。
- `question_attribution_corrections`：线程隔离、追加写入的用户纠错事件；最新事件是该线程的有效值。
- `learner_attempts.attribution_point_id`：本次作答实际贡献到的知识点，是画像重放的精确账本。
- `learner_knowledge_states`：由已生效答题证据形成的知识点聚合快照。
- `calibration_hypotheses`：probable 归因的线程级校准队列。

纠错事件额外保存 `replayed_attempts`、`retracted_calibrations` 和 `replacement_calibration_id`，因此 API 返回结果可以从数据库复核，而不是瞬时日志。

## 运行规则

提交 `POST /api/attributions/{question_id}/correction` 时：

1. 目标知识点必须处于 active 状态。
2. 未进入画像的 probable 作答会撤回旧校准，并在新知识点上创建替代校准。
3. 已进入画像且每条作答都有 `attribution_point_id` 时，系统在同一事务内：
   - 从旧知识点 Beta 计数和次数中减去对应证据；
   - 将同一证据加入新知识点；
   - 更新作答域与线程复习卡域；
   - 追加不可变纠错事件。
4. 再次纠错可以把同一证据迁回原知识点；测试覆盖 A → B → A。
5. 同一线程同一题纠正到当前有效知识点时是幂等 no-op：不新增事件、不撤回校准、不重放画像，响应标记 `deduplicated: true`。同题纠错在数据库中锁定目标知识点、基础归因与作答账本，`replayed_attempts` 只统计本次实际移动的证据。普通错题和纠错替代校准共享知识点级创建锁：SQLite 使用即时写事务，MySQL 使用知识点行锁，并发请求复用同一个 pending ID。
6. 旧数据缺少精确知识点账本，或聚合状态与账本不一致时返回 HTTP 409。系统不得依据“当前全局标签”猜测历史归因。
7. probable 弱点假设只使用 confirmed 归因题做校准；已展示但未作答的题在刷新后继续恢复，不重复占用展示预算。并发刷新也会串行复用同一待答题，只占一个证据槽和一次展示预算；内部 attempt ID 不出现在面向客户端的校准证据中。
8. 两条不同可靠题结果一致时，假设进入 `confirmed` 并一次性把暂存证据纳入画像。证据矛盾且题源耗尽、没有任何可靠题，或线程展示预算耗尽时进入 `inconclusive`：流程终止但不形成归因/能力结论，也不写入画像。
9. 同一校准题重复或冲突提交时，所有请求仍保留在原始作答账本中，但校准证据以第一次答案及其精确 attempt ID 为准；确认时必须匹配同一原始作答及正确性，每题最多一条作答可标记为 `profile_applied`。并发冲突不会覆盖首次证据。`pending → confirmed`、证据认领和知识状态增量由单个数据库事务提交；故障会整体回滚，重复确认不会再次累加。FSRS 复习卡在核心事务后更新，失败只记录错误，避免客户端因假失败重试制造新证据。

## 灰度观测口径

`GET /api/stats?thread_id=...` 的 `attribution_evidence_channels` 分开报告：

- `system_candidates`：系统候选的 confirmed / probable / unverified 数量。
- `user_corrections.events`：纠错事件数。
- `user_corrections.profile_replays`：实际重放长期画像的纠错事件数。
- `user_corrections.calibration_replacements`：创建替代校准的纠错事件数。
- `user_corrections.calibrations_retracted`：被纠错撤回的校准总数。
- `calibration_outcomes`：校准 pending / confirmed / retracted / inconclusive 数量；`inconclusive` 表示题源或预算耗尽后仍无法形成一致证据。

这些字段是运行过程计数，不衡量模型在独立 holdout 上的准确率。归因开发报告中的 `calibration_resolution_rate` 只把 confirmed / retracted 放入成功分子；分母只包含明确标记已进入校准、实际呈现次数大于零，或旧格式中已有证据的假设。未呈现过题目的终态仍计入 outcomes 以供审计，但不进入解决率分子或分母。

`GET /api/attribution-observability?thread_id=...&since=...` 提供专门的线程级灰度聚合。`since` 是可选的 Unix 时间戳且采用 `created_at >= since`，用于发布前后窗口对比。响应包含：

- `events`、`unique_questions` 和 `repeat_events`：区分反馈总量与同题反复修改；
- `reason_provided_events`：只统计非空依据数量，不返回理由正文；
- `profile_replays`、`calibration_replacements`、`calibrations_retracted`：纠错后实际动作；
- `by_target_domain` 和 `by_previous_status`：定位反馈集中域和原归因状态；
- `window.latest_event_id`：供观测方确认读取到的最新事件位置。
- `ledger_integrity`：当前线程的校准账本结构快照，包含 confirmed 证据缺失/重复/意外认领、精确 attempt ID 或正确性错配、非 confirmed 已入画像、孤儿校准引用和分类异常总数。精确 attempt ID 缺失的旧证据按正确性核验；同一作答可能同时触发重复与错配分类，因此总数是分类计数之和，不等同于唯一异常作答数。`snapshot_scope` 固定为 `current_thread_not_event_window`，明确它不受纠错事件的 `since` 窗口影响。

端点不返回题干、理由正文或其他线程明细；无事件窗口返回稳定零值和空分组。账本正常时中文灰度卡显示“完整性正常”，异常时进入警示态并只展示异常总数。响应固定携带 `metric_semantics: operational_feedback_not_accuracy` 与 `not_accuracy_metric: true`。完整性异常是结构漂移计数，不是模型错误率；系统也没有记录每一次“用户看到但未纠正”的归因曝光，因此不存在可信分母，不提供纠错率或准确率。

## 分页归因审阅

`GET /api/attribution-review?thread_id=...` 按题目 ID 升序返回审阅行。`limit` 默认 30、允许 1..100；`after_question_id` 是上一页的 `next_cursor`，下一页只读取更大的题目 ID；可选 `question_id` 按子串筛选。响应包含 `items`、筛选范围的 `total`、`has_more` 和 `next_cursor`。输入完整题号仍可能匹配以它为前缀的其他题号，因此界面保留每行的完整 ID。

接口只把指定线程每道题的最新纠错覆盖到当前页，不改变全局系统候选，也不加载其他线程的纠错。分页回归测试核对顺序、无重复、筛选结果及跨线程隔离；画像视图使用同一最新纠错查询，避免审计导出每页 500 条的上限影响当前有效值。

审阅行还提供 `question_stem`、`question_options` 和当前有效候选的 `candidate_point_name`。题目内容来自刷题使用的同一题库视图：数据库 `questions` 表为空时使用题库 JSON；不会把答案或解析放进审阅响应。知识点中文名按纠错覆盖后的 ID 读取，缺少名称时仍保留 ID 供追溯。

## 线程级审计导出

`GET /api/attribution-corrections` 只返回指定 `thread_id` 的追加式纠错事件，并包含事件 ID、前后知识点、理由、画像重放数、撤回校准数、替代校准 ID 和创建时间。

接口按事件 ID 倒序返回，使用 `limit=1..500` 控制页大小。若还有后续数据，把本页最后一条事件的 `id` 作为下一次请求的 `before_id`；服务端使用 `id < before_id` 继续读取，因此并发追加新事件不会造成翻页重复或漏读。空线程 ID、超长线程 ID和非法游标均返回 HTTP 422。

该 500 条上限只约束审计导出页，不约束画像视图。`GET /api/stats` 按线程在数据库侧为每道题选取最新纠错，
不会因为事件较旧而漏掉该题当前有效的纠错；回归测试验证最近 500 条之外仍能显示该题的最新纠错。

自动测试覆盖跨线程隔离、两页连续读取、ID 集合不重叠，以及其他线程问题 ID 不出现在导出结果中。

## 中文页面操作

“薄弱点画像 → 题目归因审计”每一行提供“纠正”按钮和可展开的题干、选项；候选知识点显示中文名与可追溯 ID。列表默认按题目 ID 稳定分页，每批 30 道，可继续加载并按题目 ID 子串筛选；常见前缀可能匹配多道题，用户仍可在结果中辨认完整 ID。纠错操作只加载 active 知识点，要求用户选择目标知识点并可填写纠错依据。提交成功后：

纠错框可即时按知识点中文名、领域或 ID 筛选，显示匹配数量；筛选隐藏原选择后不会默认改选首个匹配项，必须明确选择才能提交。无匹配项也不会发送纠错请求。

- 审计行立即显示当前线程的“用户纠错”结果；
- 操作变为“再次纠正”；
- 页面明确提示本次是画像证据重放、替代校准，还是仅保存标签；
- 画像摘要单独显示“校准未形成结论 N 个”，不会继续伪装成待校准；
- 系统候选统计保持原始口径，不因个人纠错被改写。

浏览器验收覆盖：

- `tests/browser_attribution_correction_e2e.cjs` 使用模拟 API，覆盖分页、筛选、成功提交、请求载荷、线程 ID、同目标幂等中文提示、HTTP 409 中文提示和控制台错误；同时验证纠错反馈卡的零态、成功刷新、账本异常分类警示、口径缺失时独立降级、固定“不是准确率”标识，以及 1280px/390px 视口不产生横向溢出。
- `tests/browser_attribution_correction_live_e2e.cjs` 连接真实服务和临时 SQLite，验证 30 → 60 条无重复分页、题目 ID 子串筛选、展开题干与选项、中文候选名，以及筛选后对完整目标题号执行真实纠错。
- `tests/browser_attribution_review_qa.py` 用原生 Python Playwright 在另一份临时库上复核 1360 条总数、分页、筛选、展开题目内容、390px 无横向溢出和页面脚本错误，并生成截图供目视检查。
- `tests/run_browser_e2e.py` 统一初始化临时数据库并运行 readiness、诊断、模拟纠错观测和真实纠错链路；数据库导入使用 `--db-only`，并对三份归因构建产物做前后 SHA-256 校验，防止 E2E 反向污染开发集文件。

## 迁移与验收

Alembic head 为 `f1a2b3c4d5e6`。`tests/test_alembic_fresh_sqlite.py` 覆盖两种路径：

- 全新 SQLite 直接升级到 head，核对 revision、ORM/物理表集合、新账本列和纠错审计列。
- 先建立 head，再降至 `e0f1a2b3c4d5`，写入旧结构的作答与纠错记录，最后重新升级到 head，核对原数据保留且新列默认值正确。
- 将 `DATABASE_URL` 指向目标 SQLite、将 `CISP_DB_PATH` 指向另一个诱饵文件，确认迁移只创建目标库；应用存储层另有同样的目标分离测试。

手工执行迁移验收时必须显式设置 `DATABASE_URL`。Alembic 会把它作为权威目标，不再先按 MySQL 处理后静默回退；未设置时才沿用应用后端选择逻辑。

完整回归也必须使用从当前构建产物初始化的隔离 SQLite。仓库内默认 `data/cisp_qa.db` 是运行状态，不是测试夹具；其内容可能落后于 `data/questions.json` 和 `data/manifest.json`，不能作为可复现验收依据。

## 当前限制

迁移前已进入画像但没有 `attribution_point_id` 的历史作答不能自动修正。若未来必须处理这批数据，需要独立的人工映射和离线重建流程，并先在数据库副本上验证；不得在在线请求中推断或回填。

早期迁移脚本使用当前 ORM 元数据创建表，因此“从零只升级到某个历史 revision”不能忠实复原当时模式。新增迁移通过真实 downgrade/upgrade 往返测试约束；若要彻底消除该历史债务，应建立基线迁移，而不是改写已经发布的 revision。
